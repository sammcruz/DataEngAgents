# Fab Table Query

## Use

Use this skill when the user asks to read table contents, validate row-level outcomes, compare Bronze/Silver/Gold data, or quickly troubleshoot table data after a pipeline/notebook run.

This skill is specifically useful when:

1. `fab get` or `fab ls` only returns metadata/path details, not rows.
2. You need a fast query path with minimal setup.
3. You need repeatable validation output in automation.
4. You must explain why data is not visible yet in the SQL analytics endpoint.

Start by confirming workspace and item paths, then choose one query method below.

## Fast Path Decision

Pick the method based on intent:

1. Fastest ad hoc investigation in UI: use Lakehouse Spark SQL query explorer.
2. Read-only SQL reporting path: use SQL analytics endpoint (T-SQL).
3. CLI-first automated validation artifact: run a read-only notebook that writes JSON report to `Files/_debug`, then `fab cp` it locally.
4. Schema-only check from CLI: use `fab table schema`.

## Critical Reality Check

- `fab` currently does not provide a direct "query table rows" command.
- `fab get <.../Lakehouse/Tables/...>` is a metadata/file view path, not a row-query surface.
- `fab job run-status` is pass/fail oriented and is not a complete data-validation output channel.

## Workflow

1. Confirm target paths and table existence with `fab ls`.
2. If only structure is needed, run `fab table schema` and stop.
3. If row data is needed, choose one of:
   - Spark SQL query explorer (quickest interactive)
   - SQL analytics endpoint (read-only T-SQL)
   - Read-only validation notebook (automation-friendly)
4. If SQL endpoint does not show fresh data/schema yet, run metadata refresh (portal or API) and retry.
5. Report what was validated (counts, keys, mismatches) and how it was validated.

## Commands

List lakehouse tables:

```bash
fab ls "<workspace>.Workspace/<lakehouse>.Lakehouse/Tables"
```

Show Delta schema quickly:

```bash
fab table schema "<workspace>.Workspace/<lakehouse>.Lakehouse/Tables/<schema>/<table>"
```

Copy a generated validation report from OneLake:

```bash
fab cp "<workspace>.Workspace/<lakehouse>.Lakehouse/Files/_debug/<report>.json" "/tmp/<report>.json" -f
```

## Query Methods

### A) Lakehouse Query Explorer (Spark SQL, fastest interactive)

Use this when you need immediate exploration and can work in the UI.

- Open the lakehouse.
- Use `New SparkSQL Query`.
- Run Spark SQL directly against lakehouse tables.
- Good for quick joins, checks, and exploratory debugging.

Notes:
- Query explorer supports Spark SQL (including DML/DDL), not T-SQL.
- Results grid is capped (default 1,000 rows in UI); use exports or notebook for bigger diagnostics.

### B) SQL Analytics Endpoint (T-SQL, read-only)

Use this for SQL-first analysts or read-only diagnostics.

Example checks:

```sql
SELECT TOP (100) *
FROM dbo.orders;

SELECT
  region,
  customer_id,
  order_id,
    COUNT(*) AS line_count
FROM dbo.orders
GROUP BY region, customer_id, order_id;
```

Notes:
- SQL analytics endpoint is read-only over autogenerated lakehouse Delta tables.
- Only Delta tables in `/Tables` are queryable through this endpoint.
- If a table is missing or stale, run metadata refresh and retry.

### C) Notebook Validation Report (best for CLI automation)

Use this when you need reproducible evidence in CI/CD or agent workflows.

Pattern:

1. Create/run a read-only notebook query.
2. Write compact JSON into `Files/_debug/<report>.json`.
3. Pull it with `fab cp`.
4. Delete temporary debug notebook if one was created.

Minimal example cell:

```python
import json
from pyspark.sql import functions as f

table_name = "silver.orders"
df = spark.table(table_name)

report = {
    "table": table_name,
    "row_count": df.count(),
    "sample": [r.asDict(True) for r in df.limit(20).collect()]
}

mssparkutils.fs.mkdirs("Files/_debug")
mssparkutils.fs.put(
  "Files/_debug/orders_report.json",
    json.dumps(report, default=str, indent=2),
    True
)

print(json.dumps(report, default=str, indent=2))
```

## Metadata Sync Playbook (SQL Endpoint)

If SQL endpoint results are stale:

1. Confirm the source table is Delta and under `/Tables`.
2. Trigger refresh from SQL endpoint UI (`Refresh`).
3. For automation, call the SQL endpoint metadata refresh REST API.
4. For data-only refresh in new metadata sync endpoints, prefer table-level refresh stored procedure where available.

## Guardrails

- Do not claim row-level validation from `fab get` table paths alone.
- Do not claim business validation from `job run-status` alone.
- Keep validation notebooks read-only unless user explicitly asks for writes.
- Remove temporary debug notebooks/artifacts after verification.
- If using OneLake APIs, remember they are file APIs; they do not replace SQL query engines.

## Troubleshooting

- Table visible in Spark but not in SQL endpoint:
  - Validate Delta format and location under `/Tables`.
  - Refresh metadata.
  - Check sync lag and workspace load.

- Query is slow in SQL endpoint:
  - Investigate small-file fragmentation in Delta table.
  - Run regular table maintenance/OPTIMIZE on Lakehouse side.

- Need T-SQL in notebook:
  - In Python notebook, use `notebookutils.data.connect_to_artifact(...)` (preview) for T-SQL access.

## Output

When using this skill, summarize with:

2. Exact tables checked.
3. Evidence type (counts, key-level mismatch, sample rows).
4. Any freshness caveat (sync lag/refresh needed).
